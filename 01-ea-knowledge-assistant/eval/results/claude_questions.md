## 1. How to read this report

Each question is scored by automatic checks. None of them is a human opinion:

| Check | Question it answers | How it's decided |
|---|---|---|
| **Rank** | Did search put the right document near the top? | Position (1 to 5) of the first retrieved passage from a labelled document. "miss" = none in the top 5. |
| **Right passage** | Did the passage holding the key fact reach the model? | The key fact appears in a retrieved passage from a labelled document. Rank can be 1 while this is "no": right document, wrong section. |
| **Found** | Did the assistant answer, or say "not found"? | Answerable questions should be answered; out-of-corpus ones refused. |
| **Key fact** | Is the answer actually right? | The answer text contains the labelled fact (e.g. `2025-06-30`). |
| **Cites source** | Did it cite a document that really answers the question? | At least one citation is a labelled document. |
| **Support** | Is every claim backed by the passage it cites? | Share of factual sentences that cite a passage and share at least 50% of their content words with it. "Grounded" means 90% or more. |

Verdicts combine those checks:

- ✅ **PASS**: answered, key fact present, relevant source cited, grounded (or, for out-of-corpus questions, correctly refused).
- 🟡 **PARTIAL**: the answer is correct, but the evidence trail is weaker than it should be (some sentences uncited, or the citation points to a document outside the labels).
- ❌ **FAIL**: wrongly refused, key fact missing, or (for out-of-corpus) answered with a guess.

# Approved Pattern for Asynchronous Integration Between Domains

**Mandatory pattern: INT-P1 Domain Event Publication** [2]

Domains publish immutable business events (e.g. "shipment.milestone.recorded.v1") to the Harbourline Event Backbone; consuming domains subscribe [1][2].

## Key Requirements

- **Transactional outbox (CDC):** When an event must be consistent with a database write, the producer MUST write the event to an outbox table in the same transaction, then relay via change-data-capture connector (ADR-0038) [2]
- **No dual writes:** MUST NOT commit to database and separately call Kafka in application code for authoritative events [2]
- **No polling:** Polling another domain's API to detect change is non-conforming [1]; MUST NOT be used where an event exists or can reasonably be published [2]
- **Local read models:** If a consumer needs a current view of another domain's state, build it via INT-P2 [1]
- **Event naming & schema:** Follow STD-EVT-003 rules (Avro, Schema Registry, naming convention, 7-day retention, 1 MB limit) [5]

## MuleSoft Transition

No new MuleSoft flows after **2025-06-30**; all must migrate to INT-P1 (or INT-P3 for synchronous façades) by **2026-12-31** [1][4].

Apply **RA-01 - Event-Driven Domain Integration** as your implementation blueprint [3].

# Shipment Status Updates to Customer Portal

The customer portal (Harbourline Connect, APP-050) receives shipment status updates via **Event-Carried State Transfer** [1][4]:

**Flow:**
- Harbourline Shipment Platform (HSP, APP-022) publishes two event types to the Event Backbone when milestones occur: `shipment.milestone.recorded.v1` (events: booked, gated-in, loaded, departed, arrived, discharged, customs released, delivered) and `shipment.status.changed.v1` (aggregate status) [1][4]

**Performance:**
- Measured p95 latency from HSP commit to portal read model visibility: ~11 seconds (August 2026) [4]
- Achieves the target of milestone events visible to customers in under 5 minutes for 95% of shipments (REQ-HSP-014) [1]

**Deployment:**
- US deployment in East US 2 cluster [4]
- EU deployment in West Europe cluster (ADR-0041) so EU customer data stays in-region [4]

This approach decouples portal availability from HSP (portal serves last-known state even if HSP is down) while keeping HSP as the single system of record [2][4].
